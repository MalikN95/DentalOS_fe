# DentalOS Frontend

Dental Practice Management System (DPMS) web client.

## Stack

- Next.js 16 (App Router), React 19, TypeScript (strict)
- TanStack Query (React Query) — server state
- Redux Toolkit — client state (auth), typed hooks
- React Hook Form + Zod — forms and validation
- TanStack Table — data grids
- FullCalendar — appointment scheduling
- React Flow (`@xyflow/react`) — treatment plan diagrams
- openapi-fetch + openapi-typescript — typed API client generated from backend Swagger

## Requirements

- Node.js 22+
- Running DentalOS backend (for API codegen and data)

## Getting started

```bash
# 1. Install dependencies
npm ci

# 2. Configure environment
cp .env.example .env.local

# 3. (optional) Generate typed API client — backend must be running on :4000
npm run codegen:api
# then re-export `paths` from src/common/types/api-schema.d.ts in src/common/types/api.ts

# 4. Start dev server
npm run dev
```

App: `http://localhost:3000`

## Docker

```bash
docker build -t dentalos-fe \
  --build-arg NEXT_PUBLIC_API_URL=https://api.example.com \
  --build-arg NEXT_PUBLIC_WS_URL=https://api.example.com \
  .
docker run -p 3000:3000 dentalos-fe
```

`NEXT_PUBLIC_*` variables are inlined at build time, so they are passed as build args (standalone output).

## UI kit

Components follow the Dashlab Figma design system. Design tokens (colors, radii, focus ring) are CSS variables in `src/app/globals.css`. Live showcase: `/ui-kit` route. All components are pure UI with optional `className`/`style`/`onClick` props.

### Modal

`Modal` is the single shell for every dialog (`PatientFormModal`, `CreateAppointmentModal`, `CreateBranchModal`, `SaveSettingsModal`). It owns the overlay, sticky header and sticky footer, while only the body scrolls — so long forms can never push the action buttons out of the viewport.

- `title`, `children` (body), `footer` (usually two `Button`s), `size` — `sm` 420px / `md` 640px (default) / `lg` 880px
- `onSubmit` — when passed, the header/body/footer are wrapped in a `<form>`, so a `type="submit"` button in the footer submits the body fields
- `onClose` — renders the × button, closes on overlay click and on `Escape`; `isLocked` blocks all three (e.g. while saving)
- Overflow affordances come from the `useScrollShadow` hook (`src/hooks/useScrollShadow.ts`): a gradient shadow appears at the top and/or bottom edge only in the direction that can still be scrolled, plus a chevron button in the bottom-right that scrolls one screen down while more content is hidden. Content growth (conditional fields, async data) is tracked via `ResizeObserver`.
- Autofill safety net: browser/password-manager autofill sets input values without the events React listens to, so react-hook-form would validate stale empty values ("Укажите имя" on a visibly filled field). On submit the modal calls `replayAutofill` (`src/helpers/autofill.ts`), which re-dispatches native `input`/`change` events — React skips controls whose value it already knows, so only the out-of-sync ones are flushed into form state.
- Body scroll is locked while a modal is open. Labels are localizable via `closeLabel` / `scrollHintLabel` (`common.close`, `common.scrollForMore`).

### PhoneField

`PhoneField` (`src/components/ui/PhoneField/`) is a masked phone input defaulting to the +996 (Kyrgyzstan) country code — same value contract as `TextField` (`value`/`onChange`/`onBlur` strings), so it drops into a `Controller` render prop wherever a plain phone `TextField` used to sit (patient/staff/branch/clinic forms, the patient-portal OTP login). The `+996` prefix is always shown and can't be typed over; only the 9-digit national number is actually editable, keystroke by keystroke (same digit-buffer technique as `TimeSelect`'s HH:mm mask). The committed value is space-free (`+996700123456`, for compatibility with plain E.164-style validation like the OTP login's `PHONE_PATTERN`); spaces (`+996 700 123 456`) are display-only. A record already saved under a different country code (e.g. legacy `+7...` data) is detected once on mount and left as plain, unmasked free text instead of being silently rewritten into a bogus KG number.

CTAs are `mailto:` links (no lead-capture backend yet).

- Cookie consent (`src/components/layout/CookieConsentBanner`) — mounted globally in the root layout, so it appears on every page (landing, login, dashboard, booking widget). Shows a bottom bar (Accept all / Reject non-essential / Customize) on first visit; the choice is written to a `dentalos_cookie_consent` cookie (12-month expiry, `helpers/cookie-consent.ts`) and not asked again. "Customize" opens a preferences panel with three categories — Necessary (locked on), Analytics, Marketing — each a `SwitchToggle`. Any page can reopen the panel via `openCookiePreferences()`, which the banner listens for through a `window` custom event (used by the landing page footer and the `/cookie-policy` page).

Layout is a two-column shell: a gradient brand panel (tagline + feature list + security note, all from `t.login`) and the form panel (email/password with leading `MailIcon` / `LockIcon`, password visibility toggle). The top-nav logo and the "Дашборд" nav item both link here.

- Layout: the `(dashboard)` route group shares a single `layout.tsx` that renders `DashboardShell` (client component: Redux user, logout). The shell derives the active nav item from the pathname (`getNavItemByPathname`, matching against both nav lists below) and renders two bars:
  - `TopNav` (`components/layout/TopNav`) — logo, a patient search box (submits to `/patients?search=`), the page nav (icon-over-label pills, `NAV_ITEMS` in `common/constants/navigation.tsx`, plus a "+ New patient" shortcut to `/patients?new=1`), `NotificationBell` (see Notifications below), user avatar/role and logout — which persists across navigation. The user block links to `/account`; the avatar renders the real photo (`userAvatarUrl`) when set, initials otherwise. `DashboardShell` calls `useSyncProfileFromServer` once per session to replace `/login`'s email-derived placeholder name with the real `firstName`/`lastName`/`avatarUrl` from `GET /api/auth/me`.
  - `BottomNav` (`components/layout/BottomNav`) — a floating dark pill bar fixed to the bottom-center of the viewport, listing `BOTTOM_NAV_ITEMS` (currently Chats, Tags, Reviews — kept in a separate array from `NAV_ITEMS` so it renders independently of the top bar; each item still supports the same optional `roles` filter as a top-nav item, e.g. Reviews is `['owner','admin','doctor']`). It's a `z-index: 1000` overlay on top of page content (not reserved layout space, so it never shrinks the scrollable content area). A pin button on the bar toggles `useBottomNavPin` (persisted to `localStorage`, same lazy-init-with-`typeof window`-guard pattern as `LocaleProvider`'s language): pinned (default) keeps the bar always expanded; unpinned collapses it to a high-contrast handle bar flush with the bottom edge of the viewport, which expands with a CSS transition on hover or click and collapses again on mouse-leave.
  - `Sidebar`/`Header` and the icon-rail collapse concept (`useSidebarCollapse`) were removed when the nav moved from a left rail to the top bar.
- Responsive top nav: below 1024px the inline search box and nav pills hide behind a burger button (`useMobileNav`, `MenuIcon`/`CloseIcon`) that drops down a full-width panel with the search box, every nav item as a labeled row, and logout. Opening it renders a backdrop overlay, locks body scroll and closes on `Escape`, backdrop click, or navigating to a link; the route change also closes it (effect on `pathname` in `DashboardShell`). Below 1180px the clinic name and the user's name/role are hidden first to make room (avatar and icons stay). `BottomNav` itself just scrolls horizontally on narrow screens (labels hide below 480px, icons stay).

## Notifications

Four channels exist: Email, WhatsApp, browser Push (Firebase Cloud Messaging), and In-app. Patients only get Email/WhatsApp toggles (no dashboard login, so no in-app inbox or push); staff get all four.

- **Preference toggles** — `PatientFormModal` (create/edit) has an "Уведомления" fieldset with Email/WhatsApp `SwitchToggle`s (`usePatientForm`'s `notifyEmail`/`notifyWhatsapp` fields, mapped to `patient.notificationPreferences`); `PatientInfoPanel`'s read-only view shows the enabled channels as tags. `StaffFormModal` and the inline-edit `StaffDetailContent` both have the same fieldset with all four channels (`useStaffForm`'s `notifyEmail`/`notifyWhatsapp`/`notifyPush`/`notifyInApp`, mapped to `member.notificationPreferences`); `StaffDetailContent`'s read-only mode shows the same as tags.
- **In-app bell** (`components/layout/NotificationBell`) — replaces the old static bell (`notificationsCount={3}` hardcoded in `DashboardShell`) with real data: `useNotifications` (React Query, polls `GET /api/notifications` every 30s, since the backend's WebSocket gateway isn't wired to this yet), a dropdown panel listing recent notifications (click to mark read, "Прочитать все" to mark all), and an inline "Включить push-уведомления" prompt when push permission hasn't been requested yet.
- **Web push (FCM)** — `helpers/firebase.ts` lazily initializes the Firebase client SDK only if `NEXT_PUBLIC_FIREBASE_*` env vars are set (`isFirebaseConfigured()`); `hooks/usePushNotifications.ts` requests `Notification` permission, gets an FCM token (`getToken`, needs `NEXT_PUBLIC_FIREBASE_VAPID_KEY`), registers it with the backend (`POST /api/notifications/push-subscriptions`), and listens for foreground messages (`onMessage`) to surface as a toast. Background messages (tab not focused) are handled by the service worker at `/firebase-messaging-sw.js` — served by a route handler (`src/app/firebase-messaging-sw.js/route.ts`), not a static file in `public/`, since it needs the (public, non-secret) Firebase config injected server-side.
- Nothing here requires real WhatsApp/Firebase credentials to work in dev — every piece degrades gracefully (no push prompt, backend senders log-and-no-op) until `.env` is filled in.

## Patient portal (`/portal/[slug]`, `/patient`)

A separate, mobile-first patient-facing area alongside the staff `(dashboard)` group — same app, same deploy, gated by the `patient` JWT role instead of a staff one.

- **Login** — `/portal/[slug]` (`PortalLoginPageContent`, public, pre-auth), a two-step phone → WhatsApp-code form (`PhoneOtpForm`, logic in `usePortalLogin`). The code is 4 digits (matches the backend's `SmsVerifyDto`). Requests go through `publicApiFetch` against the clinic-scoped backend routes (`/api/auth/{slug}/sms/request` / `/verify`, see backend README). On success, `AuthUser` gets a `clinicSlug` field (new, optional — staff logins never set it) so the guard below can send an expired/logged-out patient back to their own clinic's login instead of `/login`.
- **Booking confirmation CTA** — after a successful public booking (`/book/[slug]`), `BookingConfirmationStep` now also shows a "Log into patient portal" card linking to `/portal/{clinicSlug}`, nudging the patient to create/use their portal account right after booking to see the appointment and stay in touch.
- **Authenticated pages** — route group `src/app/(patient-portal)/` (URL-invisible, mirrors `(dashboard)`): `/patient` (home — next appointment + two `AccordionSection`s for Appointments/Messages counts), `/patient/appointments` (upcoming/past `Tabs`, cancel via `Modal` + reason), `/patient/messages` (thread of `MessageBubble`s + `MessageComposer`). Shared layout is `PatientPortalShell` (`components/patient-portal/PatientPortalShell`) — logo header + bottom tab nav, no sidebar — which calls `usePortalAuthGuard` (like `useRequireAuth`, but also checks `role === 'patient'` and redirects to `/portal/{clinicSlug}` instead of `/login`).
- **Data**: `helpers/patient-portal.api.ts` (fetch functions) → `usePortalProfile`/`usePortalAppointments`/`usePortalCancelAppointment`/`usePortalMessages`/`usePortalSendMessage` (React Query, same pattern as every other feature here) → page content components. Presentational pieces (`AppointmentCard`, `MessageBubble`, `MessageComposer`, `AccordionSection`, `PhoneOtpForm`) live under `components/patient-portal/`, pure UI per the usual component rules, built on the existing UI kit (`Button`, `TextField`, `Modal`, `Badge`, `Tabs`, `EmptyState`).
- Messages reuse the backend's shared patient-message log (`ApiPatientMessage`, `common/types/chat.ts`) — it now carries a `direction` (`outbound`/`inbound`) and a `portal` channel value alongside `email`/`whatsapp`, so a patient's reply from `/patient/messages` shows up in the staff `/chats` thread for that patient, and vice versa.
- New `patientPortal` namespace added to all three locale dictionaries (`ru`/`en`/`ky`).
- **Dev/QA login code reveal** — on the staff `/patients/[id]` page, `PatientInfoPanel` shows a masked "Login code" row with an eye-icon toggle (`usePatientDevLoginCode` → `GET /api/patients/:id/dev-login-code`) when the backend has one to show — which, by design, is only while WhatsApp isn't actually configured (see backend README). In a real deployment the row simply doesn't render (`code` comes back `null`).
- **Responsive shell** — `PatientPortalShell` adapts width instead of staying pinned at a phone-sized `max-width`: full-bleed below 720px, a centered `max-width: 720px` card with a hairline border above it. The bottom nav is a floating dark pill (`position: fixed`, centered on the viewport, same `#363853` color as the staff dashboard's `BottomNav`) rather than a full-width bar, so it reads the same on a phone or a wide desktop window.
- **Reviews** — on `/patient/appointments`, a completed appointment's `AppointmentCard` shows either "Leave a review" or (if one exists) the star rating + "Edit review", both opening `ReviewModal` (`StarRatingInput` — interactive when given `onChange`, read-only display otherwise — plus a comment field). Backed by `usePortalReviews`/`usePortalSubmitReview` → `GET /api/patient/reviews` / `PUT /api/patient/appointments/:id/review`; submitting again on the same appointment edits the existing review instead of creating a second one.
- **Who cancelled** — `AppointmentCard` shows "Cancelled by you" / "Cancelled by the clinic" next to the reason (`PatientPortalAppointment.cancelledBy`, backend-computed). The staff `AppointmentManagePanel` shows the equivalent (`Appointment.cancelledBy: { name, isPatient }`, mapped in `appointments.mapper.ts`) in place of the old generic "final status" note once an appointment is cancelled — same data, both directions.
- **Currency**: `formatMoney` (`helpers/appointment-status.ts`) special-cases `KGS` to render as `"1 500 сом"` instead of Intl's ICU fallback (`"1 500 KGS"` — most locales/ICU builds have no dedicated symbol for it). Single shared helper, so this fixes every call site (appointments, patients, finance, patient portal, ...) at once.
- **Booking a new appointment**: `/patient/book` (`PatientBookingPageContent` + `usePortalBookingWizard`) mirrors the public widget's `useBookingWizard` step-for-step (service → doctor → date/time → confirm — the branch is derived from the chosen doctor, never asked for directly) but skips the contact-info step since the patient is already logged in. Same `BookingBranch`/`BookingServiceCategory`/`BookingDoctor`/`BookingConfirmation` types as `common/types/booking.ts`, just fetched from `/api/patient/booking/*` with `apiFetch` instead of `/api/booking/:clinicSlug/*` with `publicApiFetch`. A "Записаться" tab was added to `PatientPortalShell`'s bottom nav for it — which also gained an explicit `z-index: 1000` (same as the staff dashboard's `BottomNav`) after testing found the global `CookieConsentBanner` (`z-index: 200`, also viewport-fixed-bottom) could otherwise sit on top of it and swallow taps.
- **Header** — `PatientPortalShell`'s header is `position: fixed` (not `sticky`) so it never scrolls out of view, with `.content`/`.contentNoNav` carrying a matching `padding-top` to clear it. It shows the current page's nav label as the title (derived from `pathname`, no more per-page `<h1>`) instead of the logo. On `/patient/messages` — the one page where the bottom nav is hidden in favor of a pinned `MessageComposer` — the header also gains a back chevron (→ `/patient`) since hiding the nav there would otherwise leave no way out of the thread.
- **Compact mobile nav** — below 480px, the bottom nav's item labels hide (icon-only) and padding shrinks, so four tabs plus the "Записаться" one fit without wrapping or horizontal overflow on narrow phones; the nav's own `overflow-x: auto` (scrollbar hidden) is the fallback for anything narrower still.

## Platform admin (`/admin`)

A separate, platform-wide area for the `super_admin` role — manages clinics across the whole platform instead of being scoped to one. Same login form, same JWT, different landing page and chrome.

- **Role & auth** — `super_admin` users have `clinicId: null` (the backend nullable-clinic-id migration); `AuthUser.clinicId`/`JwtPayload.clinicId` are typed `string | null` to match. `useLoginForm` and `/login`'s "already authenticated" redirect both branch on `role === 'super_admin'` → `/admin` instead of `/dashboard`. `DashboardShell` bounces a super_admin who lands on `/dashboard` straight back to `/admin` (it has no clinic, so the clinic-scoped hooks there would just error); conversely `SuperAdminShell` bounces any non-super_admin back to `/dashboard`.
- **Shell** — `src/app/(admin)/layout.tsx` renders `SuperAdminShell` (`components/layout/SuperAdminShell`), a role-guarded wrapper analogous to `DashboardShell`, topped by `SuperAdminTopNav` (`components/layout/SuperAdminTopNav`) — a red/maroon bar (new `--color-maroon-500`/`--color-maroon-600` tokens in `globals.css`) with two tabs (Statistics/Clinics), user block, logout. Pure presentational, no Redux/API calls of its own.
- **Statistics tab** (`/admin`, `AdminStatsPageContent`) — 4 `StatCard` tiles (total clinics/doctors/patients/revenue) plus three hand-rolled inline-SVG chart primitives under `components/charts/` (`DonutChart`, `LineChart`, `AreaChart` — no charting library, matching this codebase's no-dependency UI style; both line/area ship a hover crosshair + tooltip): an active/blocked clinics ring, a revenue-by-month line, and a clinics-growth-by-month area. Backed by `usePlatformOverview`/`usePlatformRevenueByMonth`/`usePlatformClinicsGrowth` (`hooks/usePlatformStats.ts`) over `GET /api/platform/stats/{overview,revenue-by-month,clinics-growth}`.
- **Clinics tab** (`/admin/clinics`, `AdminClinicsPageContent` + `ClinicsTable`) — search, add/edit (`ClinicFormModal`, mirrors `PatientFormModal`'s React Hook Form + Zod pattern via `usePlatformClinicForm`), block/unblock (`PATCH .../:id` with `{isActive}` — reuses the clinic's own existing `isActive` gate, so a blocked clinic's staff immediately can't log in or resolve their booking widget, no separate "blocked" column needed) and soft-delete, each behind a `window.confirm` (same pattern as Tags/Branches/Email templates). Pagination via the shared `Pagination` component (default 20 rows, `10/20/50/100/200`). Row click → `/admin/clinics/[id]` (`AdminClinicDetailContent`) for a per-clinic drill-down: doctor/patient/revenue stat tiles + an info panel + the same edit/block/delete actions.
  - **Creating a clinic also requires its first admin user** — `ClinicFormModal` shows an extra "Clinic administrator" fieldset (firstName/lastName/email/phone/password) only in create mode (`isEditMode` hides it — editing never touches the admin account). `usePlatformClinicForm`'s Zod schema conditionally requires those fields via `.superRefine()` keyed off `isEditMode`, and `valuesToCreatePayload`/`valuesToUpdatePayload` build two different payload shapes so the `admin` field is never sent on `PATCH` (the backend's update DTO doesn't declare it, and the global `ValidationPipe` is whitelist-strict — sending it would 400).
- **Data layer** — `common/types/platform-admin.ts` / `helpers/platform-admin.api.ts` / `hooks/usePlatformClinic(s).ts` follow the same three-layer TanStack React Query convention as every other domain here (not RTK Query — nothing in this codebase uses it).
- New `admin` namespace in all three locale dictionaries (`ru`/`en`/`ky`).

## Localization (i18n)

All UI strings live in locale dictionaries under `src/common/locale/dictionaries/` (`ru`, `en`, `ky`; `ru` is the source of truth and defines the `Dictionary` type). `LocaleProvider` (in `AppProviders`) exposes `useTranslation()` → `{ t, language, setLanguage }`; components read `t.<namespace>.<key>` instead of hardcoding text. `format(template, vars)` interpolates `{name}`-style placeholders. Language is persisted in `localStorage` (`dentalos.lang`, default `ru`) and switched live from the Settings → Language selector. Adding a locale = one dictionary file typed as `Dictionary`.

## Typography

Global font is Roboto (`next/font/google`, weights 400/500/700, latin + cyrillic subsets), exposed as the `--font-roboto` CSS variable and applied in `globals.css`.

## Conventions

- Server Components by default, `'use client'` only where Redux/browser APIs are needed
- Named exports only (App Router pages/layouts are the framework exception)
- Server state via React Query, client state via Redux Toolkit
- Typed Redux hooks: `useAppDispatch` / `useAppSelector` from `src/store/hooks.ts`
- **React Compiler (`reactCompiler: true` in `next.config.ts`) + react-hook-form don't mix by default.** Reading a field with the plain `form.watch('x')` escape hatch (rather than the `useWatch` hook) for a value used in JSX — a `SwitchToggle`'s `checked` prop, an `isDoctor`-style conditional fieldset — silently stops re-rendering: the compiler memoizes across renders since `watch`'s return isn't a value it can see change, so the switch looks unclickable and the conditional fieldset never appears, with no console error. Every RHF form component in this codebase (`ServiceEditorModal`, `ClinicSettingsForm`, `CreateBranchModal`, `StaffFormModal`, `StaffDetailContent`, `PatientFormModal`) therefore does two things: uses `useWatch({ control, name })` instead of `watch(name)` for any field read directly in render, and opens with a `'use no memo'` directive (the compiler's own documented opt-out) since `useWatch` alone wasn't sufficient for compiler-memoized conditional JSX blocks derived from it (e.g. `{isDoctor ? <fieldset>… : null}`). Keep both when adding a new RHF-backed form here.

## Pre-commit

Husky runs `npm run build` (`next build`) on `pre-commit` — that is the only check. ESLint, Prettier and the commit-message format are **not** enforced on commit; run `npm run lint` / `npm run format` manually. There is no `commit-msg` hook (commitlint was removed), so commit messages are free-form.
